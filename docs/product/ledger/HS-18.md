### HS-18 · Reorg de docs — CLAUDE.md router + CAPABILITIES as SSoT funcional — `decidida` · `vig:vigente`

*Cruda (operador, 2026-07-09):* «claude.md no debe ser el repositorio de backlog/pendientes,
debe ser el puntero a todo… necesitamos hojas atómicas con información concisa y útil con
cierto tiempo de vida, lo que viene no puede estar en la misma hoja de lo que hicimos» · «los
capabilities son el SSoT de lo funcional y es nuestra documentación as-code… un hook que valide
que por nada cree código si no construye o modifica un capability y lo actualice» · «firmo el
árbol y la doctrina, granularidad de 82 está bien, separar las tecnologías del claude.md
apuntando a un archivo puntero de la arquitectura as-code» · «el claude.md debe tener tmb los
punteros a nuestra doctrina de desarrollo y capabilities».

*Desarrollo:* auditoría con datos duros expuso los 3 anti-patrones: CLAUDE.md = narrativa
histórica (~4.5k tok/sesión, no puntero) · LEDGER 26k con fichas-prosa + tabla Log duplicadas y
`Siguiente`/`Deuda` enterrados en historia · sin hoja atómica de backlog (disperso en 4 sitios).
Precedente propio = el sistema `memory/` (índice + hojas atómicas + TTL). **Árbol firmado de 4
ejes:** `CLAUDE.md` router puro · `BACKLOG.md` (futuro, item cerrado se BORRA) · `ESTADO.md`
(ahora + cifras generadas) · **`CAPABILITIES.md` (estado validado — eje ortogonal, «estado de
cuenta»)** · `LEDGER.md` índice + `ledger/HS-NN.md` (pasado, TTL archivado). Cifras GENERADAS por
`arnesia conformance` (D2) — mata el drift recurrente. `STACK.md` separa el stack como puntero a
`arch/` (arquitectura as-code).

**CAPABILITIES = SSoT funcional (marco):** cruce con las mejores metodologías (SAFe *Solution
Intent* · TOGAF *Business Capability Map* · BABOK *Maintained Requirements* · BDD *Living
Documentation*) — nombre elegido = **Business Capability Map** + mecanismo **Living Documentation**
(as-code, linkeado a checks, no prosa que se pudre). **Registro DERIVADO DEL CÓDIGO:** 7
subagentes barrieron cmd/internal/web/src-tauri → **82 capabilities** con punteros `file#Símbolo`
autoritativos + validador + estado honesto (~24 `vivo` con test/story · ~46 `sin-check` · **6
STUB**). Unidad = capability de negocio (agrupa 1..N RFs); verbos de VISION (crear·mapear·
observar·mejorar) + no-funcional. La historia de usuario = *delta* que agrega/edita/borra un
capability (el saldo).

**Doctrina de enforcement** (`docs/architecture/boundaries/codigo-traza-a-capability.md`, `proposed`): R1
integridad (todo puntero resuelve) · R2 cobertura (todo archivo fuente reclamado por ≥1
capability, sin huérfano) · R3 gate de commit (tocar código ⇒ tocar `CAPABILITIES.md`) · R4
estado generado (`vivo⟺check verde`). 3 capas: hook CC (nudge) · lefthook (bloquea) · CI
conformance. Anti-drift: puntero `file#Símbolo`, no línea. Rollout warn→block: nace `proposed`
(checks difieren honesto, enforcer pendiente = nl-judge, NUNCA pass fabricado) hasta construir el
validador `capability-trace` y medir cobertura 100% → recién ahí `enforced`.

**Hallazgos del barrido (a resolver):** ⚠ **DRIFT docs↔código** — CLAUDE.md decía «SQLite
puro-Go (modernc, WAL)» pero el código real es índice **map in-memory** + persistencia **archivos
JSON atómicos** (SQLite = fase 5 futura); cifras reales `242 checks · 38 pass · 204 deferred` vs
`240·28·212` documentadas. FE sin tests (solo stories) → muchos `sin-check`. Dead-code candidatos:
`domain/graph.go#UnidadDeTrabajo` · enums Banda/Canal/Procedencia/Origen sin comportamiento ·
`app-store.ts#toggleTheme` latente. Corregidos en `STACK.md`.
